# 솔루션 브리프 — Isilon 디렉터리 사용량 스캐너 + 글로벌 통합 포탈(HQ)

> 대기업·제조 스토리지/인프라 운영팀을 위한 초대용량 NAS 가시성·정리 솔루션
> 대상 환경: 폐쇄망 다수 데이터센터(DC), Isilon/Dell EMC 보유

---

## 1. Executive Summary

초대용량 NAS(아이실론, 한 폴더에 수천만 파일)에서는 (1) 어느 디렉터리가 용량을 쓰는지 가시성이 없고, (2) 트리 전체에 `du` 를 돌리면 메모리 폭주로 프로세스가 죽으며, (3) 여러 DC에 흩어진 스토리지를 한 화면으로 볼 표준 조망이 없습니다. 그 결과 오래 미접근한 콜드 데이터가 쌓여 비용이 낭비됩니다. 더 근본적으로, 기존 멀티스레드 스캐너조차 고지연 NAS에서 약 1,000 stat/s 천장에 부딪힙니다 — 측정해 보면 병목은 NAS 대역폭이나 DB 크기가 아니라 **직렬화**(Python GIL + 단일 락 + 단일 DB 커넥션)입니다. 본 솔루션은 **메모리 평탄 2단계 스캔**으로 `du` 폭주를 피하고, **멀티프로세스 2단 병렬(pscan)+오토튜닝**으로 직렬화를 우회하며, **분석 리포트**로 정리·예산 근거를 만들고, **글로벌 통합 포탈(HQ)**로 다수 DC를 한 화면에 모읍니다. 전부 **Python 3.6+ 표준 라이브러리만**으로 동작해 폐쇄망에 그대로 올라갑니다. 인터넷·토큰 없는 오프라인 업그레이드까지 지원합니다.

---

## 2. 비즈니스 문제

대기업·제조 환경의 스토리지 운영팀은 다음 네 가지 문제를 동시에 안고 있습니다.

- **가시성 부재.** 페타바이트급 NAS에서 "어느 디렉터리가 용량을 먹고 있는가"를 즉시 답할 수단이 없습니다. 한 폴더에 파일이 수천만 개면 사람 손으로 추적하기 불가능합니다.
- **메모리 폭주.** 가장 흔한 시도인 트리 전체 `du` 는 메모리를 과도하게 써서 프로세스가 죽는 경우가 있습니다. 결국 "용량을 알아내려다 서버를 흔드는" 역설이 생깁니다.
- **멀티 DC 분산.** 스토리지가 여러 데이터센터에 흩어져 있고 각 DC의 마운트 경로·운영 방식이 달라, 전사 차원의 **표준화된 조망**이 없습니다. 같은 논리 경로가 DC마다 얼마를 쓰는지 비교할 방법이 없습니다.
- **콜드 데이터 비용.** 오래 접근하지 않은 데이터(콜드 데이터)가 비싼 1차 스토리지에 계속 남아 용량과 비용을 잠식합니다. 무엇이 콜드인지, 누가 소유했는지 보이지 않으니 정리도 예산 협의도 시작하지 못합니다.

## 3. 왜 어려운가 — 원인 분석(측정 결과, 정직하게)

문제의 핵심은 흔히 짐작하는 "NAS가 느려서" 또는 "DB가 커서"가 아닙니다. 진단(strace/gdb 수준의 측정) 결과 병목은 **소프트웨어 직렬화**였습니다.

- 기존 **멀티스레드** 스캐너는 **Python GIL + 단일 락 + 단일 DB 커넥션 직렬화**에 묶여, 고지연 NAS에서 약 **1,000 stat/s** 천장에 부딪힙니다.
- 그래서 워커(스레드)를 8개로 늘려도 실효 처리량은 1~2배에 그칩니다. 즉 8개의 워커가 사실상 1~2개 속도로 일합니다.
- 다시 말해, **대역폭을 더 주거나 DB 엔진을 바꿔도** 이 천장은 내려가지 않습니다. 직렬화 지점을 풀지 않으면 코어를 늘려도 성능이 따라오지 않습니다.

이 진단이 솔루션 설계의 출발점입니다. 처방은 "더 빠른 디스크"가 아니라 **직렬화를 우회하는 실행 모델**입니다.

## 4. 솔루션 개요

### 4.1 메모리 평탄 2단계 스캔 — `du` 폭주 회피

트리를 한 번에 처리하지 않고 두 단계로 나눕니다.

- **1단계(탐색, top-down):** 루트부터 한 단계씩 내려가며 각 디렉터리를 `os.scandir` 로 **딱 한 번만** 훑습니다. 그 디렉터리에 직접 든 파일의 용량 합·개수·하위 목록을 즉시 SQLite에 기록하고, 다음에 방문할 목록(프론티어)도 **메모리가 아니라 DB**에 둡니다.
- **2단계(상향식 집계, bottom-up):** 가장 깊은 레벨부터 루트까지 거슬러 올라가며 `재귀 용량 = 자기 용량 + Σ(자식 재귀 용량)` 으로 합산합니다. 자식이 먼저 계산되므로 재귀 `du` 가 필요 없고 파일을 두 번 훑지 않습니다.

결과적으로 메모리에는 "지금 보는 디렉터리 한 개 분량"만 올라오고, 모든 결과는 SQLite로 흘려보냅니다. **테스트에서 파일 5만여 개를 스캔해도 스캐너 RSS는 약 24MB로 평탄**했습니다 — 트리 크기와 무관하게 메모리가 거의 일정합니다. 결과 바이트는 시스템 `du` 와 일치합니다.

### 4.2 pscan(멀티프로세스 2단 병렬) + 오토튜닝 — 직렬화 우회

3장의 GIL 천장을 푸는 처방입니다.

- **2단 병렬:** **프로세스**를 여러 개 띄워 GIL을 우회하고(프로세스마다 독립 인터프리터), **프로세스당 stat 스레드**로 NFS 왕복 지연을 은닉합니다. 1단계 자식이 프로세스 수보다 적으면 더 깊이 펼쳐 병렬 단위를 확보합니다(적응형 깊이 분할).
- **오토튜닝(자동 선택):** 새 스캔을 시작할 때 같은 영역에서 **단일 / 멀티프로세스 / 2단 병렬**을 각각 짧게(읽기 전용) **실측**해 가장 빠른 방법을 고른 뒤 본 스캔을 그 설정으로 자동 시작합니다. NAS는 영역·캐시 상태마다 빠른 방법이 다르므로(저지연 영역은 단일/threads, 고지연 영역은 pscan), 추측 대신 측정해 고릅니다.

> 운영 참고: `threads` 엔진은 전체 깊이 드릴다운이 가능하고 언제든 중지·재개됩니다. `pscan` 은 루트+1단계까지 집계하고 처리량이 크게 오르지만, 시작하면 자식 프로세스가 끝까지 돌아 **중간에 멈출 수 없습니다**. 멈출 일이 잦으면 `threads`, 빠른 용량 파악이 목적이면 `pscan` 을 쓰십시오.

### 4.3 분석 리포트 — 정리·예산의 근거

스캔하며 자동 수집한 집계로 의사결정 자료를 만듭니다.

- **파일 나이(콜드 데이터):** 수정시각 버킷별 용량/개수 → 아카이브·정리 후보 식별
- **소유자별 / 확장자별:** 누가/무엇이 공간을 쓰는지(차지백·유형 분석)
- **최대 파일 Top:** 가장 큰 파일(경로·크기·수정시각·소유자) → 정리 1순위
- **용량 소진 예측:** 같은 루트 2회 이상 스캔 시 증가 추세로 90%/가득 참 예상일 추정
- **변화 Top:** 직전 완료 스캔 대비 급증/감소·신규·삭제 디렉터리

### 4.4 글로벌 통합 포탈(HQ) — 다수 DC를 한 화면으로

각 DC에 스캐너(엣지)를 한 대씩 두고, HQ는 1개의 포탈로 전사를 통합 조회합니다. 무거운 스캔은 각 DC 내부에서만 수행되고, HQ는 **요약 + 완료된 DB 스냅샷만** 받아 가볍게 동작합니다.

- **글로벌 대시보드:** 전체 용량·스토리지 수·노드 온라인·진행 중 스캔 KPI와 지역별 롤업
- **Cross-DC 경로 비교:** 논리 경로 입력 → 노드별 사용 용량·파일 수, 최대 대비%, 드리프트/누락 판정, 디렉터리 매트릭스(행=디렉터리, 열=노드). 마운트 접두어가 다른 DC는 경로 별칭으로 매핑
- **스토리지 어레이 상태:** 설정 시 Isilon/PowerStore/Unity/PowerMax/VMAX/XtremIO/VPLEX의 용량·노드·이벤트 상태(아이실론 활성 알람 포함)
- **Prometheus `/metrics`:** 기존 Grafana 대시보드에 그대로 합류

다이어그램(글로 묘사): **각 DC의 엣지**(로컬 스토리지 스캔) → HTTP로 완료된 per-run DB의 증분 tar.gz + 메타데이터를 토큰 인증으로 전송 → **한국 HQ의 포탈**(replicas/ 로 복제 + 글로벌 대시보드 + 경로 비교). 화살표는 항상 DC→HQ 단방향(요약·스냅샷)이며, 원본 스캔 부하는 DC를 떠나지 않습니다.

### 4.5 폐쇄망 친화 — 설치·운영 단순화

- **표준 라이브러리만:** Python 3.6+ (RHEL/CentOS 7 기본 3.6에서도 동작). 웹서버·DB·자원수집이 모두 내장이라 `pip install` 없이 압축본을 풀어 바로 실행
- **사내 미러 한 줄 설치:** 엣지·포탈을 각각 한 줄로 내려받기·검증·설치·systemd 서비스 등록·기동까지 완료(업데이트 소스는 사내 미러 주소로 지정)
- **오프라인 업그레이드:** 포탈 릴리스 폴더에 패키지를 두면 각 엣지가 **인터넷·GitHub·토큰 없이** 당겨가 업그레이드(데이터·설정은 보존)
- **접근 제어:** 작업 보호 비밀번호(보기는 자유, 작업에는 비밀번호), 설정 잠금, 감사 로그, WAN 구간 토큰 인증 + TLS 권장

## 5. 기대 효과

수치로 입증된 항목은 6과 7장의 PoC 측정치뿐이며, 그 외 효과는 정성적으로 기술합니다(과장하지 않습니다).

- **가시성 확보:** "어느 디렉터리가 용량을 쓰는가"를 드릴다운·상위 표·검색으로 즉시 답합니다. 메모리 평탄 스캔이라 거대한 트리에서도 조사 자체가 서버를 흔들지 않습니다.
- **콜드 데이터 정리:** 파일 나이·소유자·확장자·최대 파일 리포트로 정리 후보를 객관적 근거와 함께 추려, 정리·아카이브 협의를 시작할 수 있습니다.
- **용량 소진 예측:** 같은 루트의 반복 스캔 추세로 90%/가득 참 예상일을 산출해, 증설·정리 시점을 미리 계획할 수 있습니다.
- **멀티 DC 표준화:** 흩어진 DC를 한 화면에 모으고, 같은 논리 경로를 DC 간 비교해 드리프트/누락을 표준화된 기준으로 봅니다.
- **폐쇄망 운영 단순화:** 표준 라이브러리·한 줄 설치·오프라인 업그레이드로, 외부 연결이 막힌 환경에서도 도입·운영·갱신 부담이 작습니다.

## 6. 성능(정직 표기)

아래는 **PoC 실측치**입니다. 동일 작업을 스레드 모델과 프로세스 모델로 돌려 비교했습니다.

| 비교 | 결과 |
|------|------|
| 스레드 1 → 8 | **0.78배** (GIL 정체로 오히려 둔화) |
| 프로세스 1 → 8 | **3.75배** (4코어에서 거의 선형 확장) |
| 4워커 기준, 프로세스 vs 스레드 | 프로세스가 스레드의 **5.48배** |

> **PoC 실측치이며, 실제 환경·NAS 지연에 따라 변동됩니다.** 절대 처리량/ETA가 필요하면 실 NAS의 cold 영역에서 `tools/bench_walk.py` 로 별도 측정하십시오. 오토튜닝은 같은 영역을 연속 측정하므로 캐시 영향이 있어 '상대 비교'용입니다.

해석: 위 수치는 3장의 진단(직렬화가 병목)과 정확히 들어맞습니다. 스레드를 늘리면 GIL 경합으로 더 느려지고, 프로세스를 늘리면 코어 수만큼 선형으로 빨라집니다. 그래서 본 솔루션은 멀티프로세스 2단 병렬을 처방으로 채택했습니다.

## 7. 대규모(6PB) 로드맵 — 네이티브 메타데이터(미검증 표기)

수십억 파일·6PB 규모의 **진짜 최적해는 파일을 걷지 않는 것**입니다. pscan은 직렬화 천장을 크게 끌어올리지만, 본질적으로 여전히 파일을 stat 하는 접근입니다. 그 규모에서는 클러스터가 이미 보유한 메타데이터를 조회하는 편이 비교할 수 없이 빠릅니다.

- **아이실론 네이티브 메타데이터:** SmartQuotas 어카운팅 쿼터, FSA/InsightIQ로 파일을 걷지 않고 클러스터 내부 메타데이터에서 디렉터리 사용량을 조회.
- **본 솔루션의 방향:** 이 네이티브 경로를 **연동하는 방향을 로드맵으로 제시**합니다. 스캐너/포탈은 이미 OneFS PAPI 상태 조회와 어레이 상태 연동 골격을 갖추고 있어, 어카운팅 데이터를 같은 대시보드·Cross-DC 비교에 합류시키는 확장이 자연스럽습니다.
- **정직성 고지:** 이 네이티브 메타데이터 연동은 **실 클러스터 미보유로 아직 검증되지 않았습니다.** 실제 클러스터 환경에서의 검증을 PoC 범위에 포함해 함께 확인하는 것을 권합니다.

## 8. 도입 절차 및 요구사항

### 8.1 단계별 도입

1. **PoC (1개 영역):** 대표 디렉터리 하나를 골라 메모리 평탄 스캔과 오토튜닝을 돌려 봅니다. 본 환경의 NAS 지연에서 어떤 엔진이 빠른지, 메모리가 실제로 평탄한지, `bench_walk.py` 로 절대 처리량은 얼마인지 측정합니다(성능은 PoC 표기 기준, 환경에 따라 변동).
2. **파일럿 (1개 DC):** 한 DC에 엣지를 설치하고 정기(예약) 스캔과 분석 리포트를 운영해, 콜드 데이터·최대 파일·소진 예측을 실제 운영 흐름에 얹어 검증합니다.
3. **확산 (전사):** 나머지 DC에 엣지를 한 줄 설치로 전개하고, 한국 HQ에 포탈을 띄워 Cross-DC 비교·KPI·Prometheus 연동을 표준 운영으로 정착시킵니다. (선택) 7장의 네이티브 메타데이터 연동을 실 클러스터에서 검증합니다.

### 8.2 요구사항

- **엣지(스캐너):** Python 3.6+ 리눅스 서버, 조사 대상 NAS를 **읽기 권한**으로 마운트(NFS/SMB), `--mount-base` 로 스캔 허용 경로 제한. 권장 구성은 `/ifs` 를 별도 리눅스 서버에 마운트해 그 서버에서 실행.
- **포탈(HQ):** 리눅스 서버 1대(기본 포트 8800), 각 엣지로의 HTTP 도달 경로, 복제 인증용 API 토큰. WAN 노출 시 TLS(리버스프록시/VPN) + HQ IP 허용 방화벽 권장.
- **권한/안전:** 마운트는 읽기전용 권장, 대시보드는 신뢰망 또는 SSH 터널로 접근, 작업 보호 비밀번호·설정 잠금 적용. 아이실론 crossmnt 환경에서는 `--one-file-system`(-x)을 켜지 마십시오(중첩 익스포트 용량이 누락됨).

## 9. 요약 + 다음 단계

초대용량 NAS의 가시성·메모리 폭주·멀티 DC 분산·콜드 데이터 비용은 따로 푸는 문제가 아니라, **직렬화라는 한 원인**과 **운영·조망의 표준화**로 함께 풀어야 하는 문제입니다. 본 솔루션은 메모리 평탄 2단계 스캔으로 `du` 폭주를 없애고, pscan+오토튜닝으로 직렬화 천장을 우회하며(PoC 실측: 프로세스 1→8 = 3.75배, 4워커서 프로세스가 스레드의 5.48배 — 환경에 따라 변동), 분석 리포트로 정리·예산 근거를 만들고, 글로벌 통합 포탈로 다수 DC를 한 화면에 모읍니다. 폐쇄망에서도 표준 라이브러리·한 줄 설치·오프라인 업그레이드로 부담 없이 도입할 수 있으며, 6PB 규모의 네이티브 메타데이터 연동은 실 클러스터 검증을 전제로 한 로드맵으로 함께 제안합니다.
