## 사용 전 주의 (발표자 필독)

- **성능 수치는 모두 "PoC 실측"** 입니다. 슬라이드·구두 모두 "PoC, 실환경에 따라 변동" 한 줄을 반드시 붙입니다.
- **없는 기능을 지어내지 않습니다.** 데모는 아래 6단계의 실재 기능만 보여줍니다.
- **가격은 "별도 문의"** 로 답합니다. 금액 기반 ROI 수치를 만들지 않습니다.
- 회사명·발표자·연락처는 `[자리표시자]` 로 두고, 발표 직전에 채웁니다.
- 경쟁 제품을 비방하지 않습니다. 사실(원인·동작)만 설명합니다.
- **6 PB 규모는 "아이실론 네이티브 메타데이터 권장(로드맵, 미검증)"** 로만 말합니다. 본 제품이 6 PB를 다 걷어 검증했다고 말하지 않습니다.

### 슬라이드 2 — 고객의 문제

**화면 핵심 메시지**
- **가시성 부재**: 어느 디렉터리/소유자/확장자가 공간을 먹는지 한눈에 안 보임
- **메모리 폭주**: 트리 전체에 `du` 를 돌리면 메모리 부족으로 프로세스가 죽음
- **멀티 DC 분산**: DC마다 따로 조사 → 전사 통합 뷰가 없음

**Talking points**
- 한 디렉터리에 파일이 수천만 개인 아이실론에서, 흔한 `du -sh` 한 방은 메모리를 너무 써서 죽거나 클러스터에 부담을 줍니다.
- DC가 여러 곳이면 각자 엑셀로 취합하게 되는데, 기준도 시점도 달라 비교가 어렵습니다.

### 슬라이드 3 — 왜 어려운가 (원인, 정직하게)

**화면 핵심 메시지**
- 단순히 "더 많은 스레드"로 해결되지 않음
- 기존 스레드 방식의 천장: **GIL + 단일 락 + 단일 DB 직렬화 → 약 1,000 stat/s**
- 워커를 늘려도 직렬화 지점에서 막힘 (측정 결과)

**Talking points**
- 이 문제를 strace/gdb로 진단해 보면 병목은 NAS 대역폭도 DB 크기도 아니었습니다. 파이썬 GIL과 단일 락, 단일 DB 커넥션이 작업을 직렬화하는 게 원인이었습니다.
- 그래서 스레드만 늘리면 8개를 줘도 사실상 1~2개 속도밖에 안 납니다. 처방은 "프로세스를 쓰는 것"입니다. 그 근거를 다음 장에서 수치로 보여드립니다.

### 슬라이드 4 — 솔루션 개요

**화면 핵심 메시지**
- **2단계 + SQLite 스캔**: 메모리 평탄(테스트 RSS ≈ 24MB), `du` 폭주 회피
- **웹 대시보드 + 분석 리포트**: 콜드 데이터·소유자·확장자·최대 파일·용량 소진 예측·변화 Top
- **글로벌 포탈(HQ)**: 멀티 DC 한 화면 — Cross-DC 비교 · 스토리지 어레이 상태 · Prometheus

**Talking points**
- 트리를 한 번에 처리하지 않고 ① 위에서 아래로 디렉터리를 한 번씩 훑어 SQLite에 기록하고, ② 가장 깊은 곳부터 거슬러 올라가며 합산합니다. 메모리에는 "지금 보는 디렉터리 하나"만 올라옵니다.
- 그 결과를 웹 대시보드로 실시간 조망하고, 분석 리포트로 "무엇을 정리·아카이브할지"까지 뽑습니다.
- DC가 여럿이면 HQ 포탈 한 화면에서 전사를 봅니다.

### 슬라이드 6 — 차별점

**화면 핵심 메시지**
- **메모리 평탄 스캔**: 트리 크기와 무관, 테스트 RSS ≈ 24MB
- **오토튜닝**: 단일/멀티프로세스/2단 병렬을 실측해 가장 빠른 방법 자동 선택
- **표준 라이브러리만**: 폐쇄망 즉시 실행, 설치 의존성 없음
- **글로벌 포탈**: 멀티 DC 한 화면 + Cross-DC 경로 비교

**Talking points**
- 핵심 차별점은 "추측이 아니라 측정"입니다. NAS는 영역·캐시 상태마다 빠른 방법이 다르기 때문에, 오토튜닝이 짧게 실측해서 가장 빠른 방법으로 본 스캔을 자동 시작합니다.
- pip 설치가 막힌 폐쇄망 서버에 압축본만 풀면 바로 돕니다. 외부 패키지가 필요 없습니다.

### 슬라이드 7 — 성능 (PoC 실측, 정직하게)

**화면 핵심 메시지**
- 기존 스레드 천장: GIL + 단일 락 + 단일 DB 직렬화 → 약 **1,000 stat/s**
- **PoC 실측**: 스레드 1→8 = **0.78배**(GIL 정체) / 프로세스 1→8 = **3.75배** / 4워커에서 프로세스가 스레드 대비 **5.48배**
- ⚠ 모두 **PoC 결과 — 실환경(NAS·영역·캐시)에 따라 변동**

**Talking points**
- 스레드를 8개로 늘리면 오히려 0.78배로 느려졌고, 프로세스를 8개로 늘리니 3.75배 빨라졌습니다. GIL을 우회한 효과입니다.
- 강조드릴 점은 이 숫자가 **PoC 실측**이라는 것입니다. 실제 클러스터·영역·캐시 상태에 따라 달라지므로, 도입 시 고객 환경에서 다시 재는 것을 전제로 말씀드립니다.

### 슬라이드 8 — 보안 · 폐쇄망

**화면 핵심 메시지**
- **폐쇄망 즉시 실행**: 표준 라이브러리만, 인터넷·토큰 불필요
- **사내 미러 한 줄 설치** + **systemd** 서비스 등록·기동
- **오프라인 업그레이드**: 포탈 릴리스 폴더에 패키지 → 엣지가 한 줄로 당겨 업그레이드
- 운영 게이트: 작업 보호 비밀번호(보기는 자유, 작업은 비밀번호)·설정 잠금·감사 로그

**Talking points**
- 외부 연결이 막힌 DC에서도 사내 미러 한 줄로 설치하고 systemd로 상시 운영합니다.
- 업그레이드도 인터넷·GitHub·토큰 없이, 포탈 릴리스 폴더에 패키지를 두면 각 엣지가 한 줄로 당겨 올립니다.
- 대시보드 자체에는 강력한 인증이 기본 내장은 아니므로, 신뢰망 사용·SSH 터널·작업 보호 비밀번호를 함께 권장합니다(정직하게 안내).

### 슬라이드 9 — 도입 절차 (PoC → 파일럿 → 확산)

**화면 핵심 메시지**
- **1) PoC**: 대표 디렉터리 1~2개로 메모리 평탄·오토튜닝·속도 실측
- **2) 파일럿**: 1개 DC에 엣지 + HQ 포탈 1대, 정기 스캔·리포트 운영
- **3) 확산**: 포탈에서 IP+계정만으로 각 DC 엣지 자동 설치·등록

**Talking points**
- 먼저 고객 환경의 대표 경로에서 직접 측정해 효과를 확인합니다(PoC 수치는 환경에 따라 다르니 직접 재는 게 가장 정직합니다).
- 파일럿에서 1개 DC를 운영해 보고, 검증되면 포탈에서 노드를 추가하며 전사로 확산합니다.

# 파트 B. 5분 라이브 데모 시나리오

**총 5분 · 6단계.** 각 단계에 시간 배분 + "클릭/멘트" 스크립트. 데모는 실재 기능만 사용합니다.

> **사전 준비(중요)**
> - 거대 스캔은 시간이 걸리므로, **미리 완료해 둔 스캔 결과 화면**(대시보드·분석 리포트·포탈)을 별도 탭에 띄워 둡니다. 라이브로 시작한 스캔이 길어지면 이 탭으로 전환해 설명을 이어갑니다.
> - 합성 트리를 미리 만들어 두면 즉석 스캔이 빨리 끝납니다: `python3 -m isilon_usage gentest /tmp/isilon_demo --dirs 10 --subdirs 5 --files 10 --size 16K -y`
> - 포탈(HQ)과 엣지를 같은 데모 머신/네트워크에 미리 기동해 둡니다.

**클릭**
- 터미널에서 사내 미러 한 줄 설치 명령 실행 (curl … | bash, 또는 압축본 풀고 `python3 -m isilon_usage`)

**멘트**

### 단계 3 — 오토튜닝 자동 선택 (1:00)

**클릭**
- 확인창에서 확인 → 첫 화면(Summary)에 **오토튜닝 실시간 표**가 뜨는 것을 보여줌
- 단일 / 멀티프로세스 / 2단 병렬을 각각 짧게 측정하고, 가장 빠른 방법이 선택되는 과정 설명

**멘트**
- "NAS는 영역·캐시 상태마다 빠른 방법이 다릅니다. 그래서 추측하지 않고, 같은 영역에서 단일·멀티프로세스·2단 병렬을 짧게 실측해 **가장 빠른 방법을 자동으로 골라** 본 스캔을 시작합니다."
- "PoC 실측에서는 프로세스를 8개로 늘렸을 때 1개 대비 3.75배, 4워커에서 프로세스가 스레드 대비 5.48배까지 나왔습니다. 다만 이건 PoC 수치이고, **실제 환경·영역·캐시에 따라 달라지므로** 도입 시 이 오토튜닝이 고객 환경에서 직접 재서 고릅니다."
- "정직하게, 연속 측정이라 캐시 영향이 있어 '상대 비교'용입니다. 절대 처리량이 필요하면 cold 영역에서 따로 재는 도구도 있습니다."

### 단계 4 — 대시보드 (진행/자원/드릴다운/리포트) (1:15)

**클릭**
- **Summary 탭**: 진행률, 확인된 사용량/전체 디스크 %, 자원 모니터(시스템 메모리·CPU·디스크, 측정 프로세스 RSS) — "스캐너 RSS가 평탄하게 유지됨"을 강조
- **디렉터리 탭**: 디스크 사용량 파이차트 클릭 → 드릴다운 트리로 하위 파고들기, 용량 상위 디렉터리
- **📊 분석 리포트 탭**: 파일 나이(콜드 데이터)·소유자·확장자별, 최대 파일 Top, 용량 소진 예측, 변화 Top

**멘트**
- "여기 측정 프로세스 메모리를 보세요. 트리가 아무리 커도 스캐너 RSS가 거의 일정합니다. 테스트에서 파일 5만여 개를 스캔해도 약 24MB로 평탄했습니다. `du` 한 방으로 죽던 문제를 이렇게 피합니다."
- "파이차트를 클릭하면 그 디렉터리 안으로 들어가며 비중을 봅니다. 그리고 분석 리포트에서 '오래된 콜드 데이터', '누가 가장 많이 쓰는지', '가장 큰 파일', 그리고 '이 추세면 언제 90%·가득 차는지' 예측까지 나옵니다 — 정리·아카이브 우선순위가 바로 나옵니다."

### 단계 5 — 포탈(HQ): 멀티 DC 한 화면 (1:00)

**클릭**
- 포탈 `http://<HQ>:8800/` 접속
- **노드 설정**: IP + 계정만으로 SSH 자동 설치·등록(또는 엣지 자기등록 `--hq`) 흐름 설명
- **글로벌 대시보드**: 지역별 롤업, 노드 표(온라인/스캔 중/오프라인) — 멀티 DC가 한 화면에
- **경로 비교(Cross-DC)** 탭: 논리 경로 입력 → 노드별 용량·파일 수 비교 + 드리프트/누락 판정

**멘트**
- "DC마다 엣지를 한 대씩 두고, HQ에서 이 포탈 한 화면으로 전사를 봅니다. 노드 추가는 IP와 계정만 넣으면 SSH로 자동 설치·등록됩니다."
- "무거운 스캔은 각 DC 안에서만 돌고, HQ는 요약과 완료된 DB 스냅샷만 받아 가볍게 동작합니다. '경로 비교'에서 같은 논리 경로를 DC끼리 나란히 비교하면 어디가 튀는지·빠졌는지 바로 보입니다."
