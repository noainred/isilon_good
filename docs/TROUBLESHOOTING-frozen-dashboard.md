# 화면이 멈췄을 때 — 스캔 프로세스가 살아있는지 확인 & 복구

대시보드 화면이 갱신되지 않을 때, **스캔 프로세스가 죽었는지/살았는지** 빠르게
판단하고 **다시 정상 동작**시키는 방법을 정리한 문서입니다.

> 결론부터: 화면이 멈춰 보여도 **스캔 자체는 살아있는 경우가 대부분**입니다.
> 거대 스캔(수천만 디렉터리)에서 per-run DB 가 커지면 대시보드 상세 조회가
> 느려져 "멈춘 것처럼" 보일 뿐입니다. 아래로 확인하고 복구하세요.
>
> 🔴 **"DB 가 너무 커져 서버가 죽을까 걱정"** 이라면(파일 수십억 개) → 바로
> [7. 서버가 죽는 것 자체를 막기](#7-서버가-죽는-것-자체를-막기-v1140--수십억-파일용-안전장치)
> 로 가세요(디스크 여유 자동 일시정지·최대 깊이·하드링크 토글).

> ✅ **가장 먼저(현재 v1.99.23): 대시보드 🔧 트러블슈팅 탭을 여세요.** 실행 중 스캔이 지금 어느
> 구간(디렉터리 읽기 readdir / stat / 합산 / DB 쓰기 / 유휴)에 있는지 워커별로 프로파일하고,
> 처리량·하트비트·프론티어·DB/디스크 상태로 **병목과 처방을 자동 출력**합니다(진단 이력도 저장).
> 📈 처리량 추이 탭도 함께 보면 됩니다. 아래 수동 절차(ls/watch/strace/top)는 그 다음 보조 수단입니다.
>
> ⚠ **멈춰 보이는 스캔이 `pscan`(멀티프로세스)이면** 시작 후 **중지·재개가 안 됩니다** — 끝까지
> 기다리거나(자식 프로세스가 끝에 결과를 한 번에 기록), 정말 멈추려면 프로세스를 종료하고 재시작하세요.
> 중지가 필요한 운영이면 스레드 엔진으로 스캔하세요.

---

## 1. 증상

- 상단 헤더가 **"대상 경로 로딩 중…"** 에서 멈춤
- **요약 / 현재 진행 상황 / 자원(메모리·CPU)** 카드가 `—` 또는 `0`
- 우측 하단 **"마지막 업데이트: —"**
- 그런데 왼쪽 **"전체 용량 관리 개요"** 는 스캔을 **탐색중**으로 보여줌(여긴 잘 뜸)

---

## 2. 30초 안에 "살아있는지" 판단하기

### (A) 가장 확실 — per-run DB 파일이 커지는지 (서버에서)

스캐너는 디렉터리를 찾을 때마다 per-run DB(`<data-dir>/scans/scan_*.db`)에
기록합니다. **파일 크기·수정 시각이 변하면 살아있는 것**입니다.

```bash
# 데이터 폴더의 scans/ 에서
ls -la <data-dir>/scans/

# 2초마다 크기 변화 관찰 (.db / .db-wal 이 커지면 = 쓰는 중 = 살아있음)
watch -n 2 'ls -la <data-dir>/scans/'
```

`.db-wal` 파일이 보이고 크기·시각이 계속 바뀐다 → **살아서 탐색 중**.

### (B) 하트비트 표시 (v1.13.0 이상)

대시보드 **Summary → 요약 → "진행 갱신(하트비트)"**:

- 🟢 `N초 전 갱신 (정상 동작)` → 살아있음
- 🔴 `60초째 갱신 없음 — 멈춤 의심` → 멈춤(아래 3·5 확인)

### (C) 개요 숫자가 느는지

"전체 용량 관리 개요"의 **조사 용량 / 확인%** 이 시간이 지나며 **증가하면 살아있음**.

## 3. 서버에서 프로세스 확인 (OS 레벨)

```bash
# 1) 프로세스 살아있나  (웹에서 시작한 스캔은 'serve' 프로세스의 스레드)
ps -ef | grep isilon_usage
ps -p <PID>

# 2) 일하는 중인가 — 워커 스레드 CPU
top -H -p <PID>
#   disc-0 .. disc-N 스레드가 CPU 를 쓰면 → 탐색 중(살아있음)
#   모든 스레드가 오래 0% → 멈춤(느리거나 행 걸린 NFS 경로 의심)

# 3) I/O 하고 있나
ls -l /proc/<PID>/fd | grep <마운트경로>     # 마운트의 열린 파일
strace -f -p <PID> 2>&1 | head -20           # getdents/stat 가 돌면 살아있음
#   한 경로에서 멈춰 있으면 → 그 경로(느린/행 걸린 NFS)에서 대기 중

# 4) 콘솔로 상태 확인 (대시보드와 무관, 가벼움)
python3 -m isilon_usage status --data-dir <data-dir>
python3 -m isilon_usage status --data-dir <data-dir> --scan <ID>
```

## 4. 왜 화면이 멈춰 보이나 (원인)

- 수천만 디렉터리 스캔은 per-run DB 가 수 GB 가 됩니다.
- 대시보드가 **자주 폴링**하며 무거운 조회를 하면 **긴 읽기 락**이 걸리고,
  그러면 SQLite **WAL(`-wal`) 체크포인트가 막혀** `-wal` 파일이 수 GB~수십 GB 로
  **부풀어** 모든 조회가 더 느려지는 **악순환**에 빠집니다 → 상세가 안 뜸.
- 스캔 자체는 살아있는 경우가 대부분(2·3 으로 확인).

> **v1.13.0** 에서 `/api/status` 를 경량화하고(불필요한 전체 정렬 제거), 스캐너가
> 30초마다 WAL 체크포인트를 하도록 고쳐 이 현상을 예방합니다.

> ⚠️ **더 위험한 경우 — 서버가 실제로 죽는다(디스크 가득 참).** 파일이 수십억 개면
> per-run DB(본 파일) + `-wal` 이 합쳐 **수십 GB** 가 되어 **데이터 디스크를 다 채울**
> 수 있습니다. 디스크가 0 이 되면 SQLite 쓰기가 실패하고 스캔/서버가 비정상 종료될
> 수 있습니다. 이건 "화면 멈춤"이 아니라 **프로세스 죽음**이라 더 치명적입니다.
> **v1.14.0 의 디스크 여유 자동 일시정지(아래 7)** 가 이걸 막습니다.

## 5. 다시 정상 동작시키기 (복구)

### (A) 즉시 — 재시작 없이 (스캔 유지, 권장 첫 조치)

1. 대시보드의 **"자동(1.5s)" 체크 해제** 하거나 **탭을 닫습니다.**
   → 느린 읽기 락이 사라져 **WAL 이 체크포인트되고 스캔이 다시 빨라집니다.**
2. 상태는 **"새로고침"을 한 번씩만** 누르거나(거대 DB 는 한 번 응답에 수 초~수십 초
   걸릴 수 있어 기다리기) **CLI `status`** 로 확인합니다.
3. 그대로 두면 **탐색 → 집계 → 완료**까지 진행됩니다(작업 안 날아감).

### (A-2) 재시작 없이 대시보드만 최신화 (v1.14.0, 스캔 그대로)

서버는 요청마다 `dashboard.html` 을 **디스크에서 새로 읽어** 응답합니다. 따라서
**`dashboard.html` 파일 하나만 교체**하면 **스캔·서버를 재시작하지 않고** 폴링
분리(개요/상세 분리 + 타임아웃) 버전을 바로 적용할 수 있습니다.

```bash
# 운영 중인 설치 경로의 dashboard.html 만 새 버전으로 덮어쓰기
cp isilon_usage/dashboard.html  <설치경로>/isilon_usage/dashboard.html
# 브라우저 강력 새로고침(Ctrl+Shift+R) → 다음 로드부터 적용
```

이러면 가벼운 **개요(`/api/scans`)는 항상 먼저 갱신**되고, 무거운 상세
(`/api/status`)는 **한 번에 하나만**(타임아웃 8초/25초) 보내져 화면이 막히지
않습니다. 진행 상황은 아래 CLI/SQL 로도 부하 없이 볼 수 있습니다.

```bash
# 단일 행 조회라 거대 DB 에서도 즉시 응답 — updated_at 이 바뀌면 살아있음
sqlite3 <data-dir>/manager.db \
 "SELECT status, discovered_dirs, sized_dirs, total_bytes,
         datetime(updated_at,'unixepoch','localtime')
    FROM scan_runs ORDER BY id DESC LIMIT 1;"
```


### (B) 근본 해결 — v1.13.0 이상으로 업데이트

1. 최신 압축본(`download/isilon_usage-latest.tar.gz`)으로 코드를 교체합니다.
2. **`serve` 재시작** → 실행 중이던 스캔은 시작 시 **자동으로 '일시정지'** 로
   정리됩니다(고아 스캔 정리).
3. 개요에서 그 스캔의 **'재개'** 버튼을 누르면 **중단 지점부터 이어서** 탐색합니다
   (프론티어가 DB 에 있어 처음부터 다시 하지 않음).

> 재시작 시 큰 `-wal` 은 DB 본 파일로 합쳐지며(체크포인트) 정리됩니다. SQLite WAL 은
> 크래시 안전하므로 프로세스를 강제 종료해도 다음 열 때 복구되어 데이터가 보존됩니다.

## 7. 서버가 죽는 것 자체를 막기 (v1.14.0 — 수십억 파일용 안전장치)

수십억 파일·초대용량 스캔에서 **DB/WAL 이 디스크를 채워 서버가 죽거나** 메모리가
부족해지는 것을 막는 설정입니다. **설정 화면** 또는 **CLI 플래그**로 켭니다.

| 설정(화면) | CLI 플래그 | 설정 키 | 효과 |
|---|---|---|---|
| **깊이 접기 N (추천)** | `--fold-depth N` | `fold_depth` | 깊이 N 까지만 **행 저장**, 그 아래는 **내려가서 용량은 다 세되** N 디렉터리에 합산 → **DB 크기 묶임 + 합계 정확**(무제한 스캔과 동일). N 아래 디렉터리별 상세만 없음 (0=끔) |
| **DB 최대 GB 자동 일시정지** | `--db-max-gb N` | `db_max_gb` | per-run DB(`.db`+`-wal`)가 N GB 초과하면 **자동 일시정지 + 사유 기록**. 깊이 접기로도 못 묶이는 폭증을 막는 안전망 (0=끔) |
| 디스크 여유 GB 미만 자동 일시정지 | `--min-free-gb N` | `min_free_gb` | 데이터 디스크 여유가 N GB 미만이면 **스캔 자동 일시정지 + 사유 기록**. 디스크가 가득 차 서버가 죽기 직전에 안전하게 멈춤 (0=끔) |
| 하드링크 중복 제거 | `--no-hardlink-dedup` | `hardlink_dedup` | 끄면 `(dev,ino)` 집합을 메모리에 안 쌓아 **메모리 절약**(용량은 중복 셈). 백업/스냅샷 등 하드링크 많은 트리에 권장 |
| 탐색 최대 깊이(빠른 컷) | `--max-depth N` | `scan_max_depth` | 깊이 N 아래는 **방문 안 함** → 가장 빠르지만 **그 아래 용량이 합계에서 빠짐**(구조만 볼 때). 정확한 합계가 필요하면 위의 *깊이 접기* 사용 (0=무제한) |

> 💡 **"DB 크기 제한 + 정확한 합계"** 가 목표면 **깊이 접기(`fold_depth`)** 를 쓰세요.
> `max_depth` 는 깊은 용량을 **누락**하므로 빠른 구조 파악용입니다.

### 권장값 (예: 32GB 데이터 디스크, 수십억 파일)

- **깊이 접기**: 보고에 충분한 깊이(예: `6`~`8`). 그 아래 수십억 leaf 는 상위
  디렉터리 용량에 **합산만 되고 행으로 안 쌓여** DB 가 크게 작아집니다(합계는 정확).
- **DB 최대 GB**: 디스크 총량을 고려해 안전한 상한(32GB 디스크면 `10`~`15` GB).
- **디스크 여유 자동 일시정지**: 디스크 총량의 약 **10~15%** (32GB → `5` GB 정도).
  일시정지되면 디스크를 확보(오래된 스캔 prune, WAL 체크포인트)한 뒤 **'재개'** 로
  중단 지점부터 이어서 진행합니다.
- **하드링크 중복 제거**: 스냅샷/백업처럼 하드링크가 많으면 **사용 안 함**으로
  메모리를 아낍니다(중복 용량을 그대로 세도 무방할 때).

### CLI 예시

```bash
# 깊이 8 까지만 행 저장(아래는 용량만 합산·합계 정확) + DB 15GB/디스크여유 5GB 안전망
python3 -m isilon_usage scan /ifs/data \
    --data-dir /var/isilon_data \
    --fold-depth 8 --db-max-gb 15 --min-free-gb 5 --no-hardlink-dedup
```

> 자동 일시정지된 스캔은 개요의 **'재개'** 로 중단 지점부터 이어집니다(프론티어가
> DB 에 있어 처음부터 다시 하지 않음). 디스크는 오래된 스캔을
> `python3 -m isilon_usage prune --data-dir <data-dir> --keep-per-root 3`
> 으로 정리해 확보하세요.
