# 성능·최적화 가이드 (측정 기반)

> 기준 버전: **v1.99.23** · 갱신: 2026-07-10
> 원칙: **측정으로 확인한 것만** 적는다. PoC 실측은 ‘실측’, 미검증은 ‘미검증’으로 표시한다.
> 이 문서의 수치는 **추측이 아니라 strace/gdb 진단 + PoC 측정**에서 나왔다.

---

## 1. 한 줄 요약

> **병목은 DB 크기도, NAS 대역폭도 아니다.** GIL + 단일 락 + 단일 DB 커넥션 직렬화다.
> 처방은 **멀티프로세스(pscan)** 다 — 코어 수만큼 처리량이 는다.

---

## 2. 측정으로 확정된 병목 (재논의·재추측 금지)

strace/gdb로 진단한 결과, 거대 스캔의 정체는 다음 **직렬화**였다:

- **GIL**(파이썬 전역 인터프리터 락) — 스레드가 CPU 구간에서 사실상 한 번에 하나만 실행.
- **단일 `_dlock`** — 디렉터리 큐/공유 상태 보호 락에서 워커들이 줄을 선다.
- **단일 DB 커넥션 직렬화** — 쓰기가 한 커넥션으로 모인다.

그 결과 **워커를 8개로 늘려도 실효는 1~2개 수준**, 대략 **~1,000 stat/s**에 머물렀다.
즉 스레드를 더 줘도 GIL/락 때문에 **선형 확장이 되지 않는다.**

---

## 3. 처방 — pscan(멀티프로세스) · PoC 실측

같은 작업을 스레드 vs 프로세스로 비교한 **PoC 실측값**:

| 구성 | 1→8 워커 처리량 | 해석 |
|---|---|---|
| **스레드** | **0.78배** | 늘릴수록 오히려 정체(GIL 경합) |
| **프로세스(pscan)** | **3.75배** | 4코어에서 거의 **선형** |
| 4워커 기준 | 프로세스가 스레드의 **5.48배** | GIL 우회 효과 |

- **결론**: 처리량이 필요하면 **엔진을 pscan(멀티프로세스)** 로. 코어 수가 곧 한계선이다.
- **주의(정직)**: pscan은 **시작하면 중간에 멈출 수 없다**(자식 프로세스가 끝까지 돌고 마지막에 결과를 한 번에 기록). 중지가 필요하면 스레드 엔진을 쓴다(`stop_scan`이 사유를 그대로 알려줌).

---

## 4. 측정상 ‘무의미’했던 것 (하지 말 것)

추측으로 손대기 쉬우나, **측정상 효과가 없었던** 것들:

- **DB 엔진 교체 / 저장형식 변경(CSV 등)** — 쓰기는 한가했다. 병목이 아니므로 **무의미**.
- **fold‑depth를 ‘속도 손잡이’로 오해** — fold‑depth는 **DB 크기/행 수를 묶는 것**이지 속도와 직결되지 않는다.
  - 깊은 중첩 트리: 디렉터리 수를 줄여 **도움**.
  - 납작한 거대 디렉터리(한 폴더에 파일 수백만): **효과 거의 없음**.
  - fold도 용량을 세려고 파일을 stat 한다(공짜 아님).

## 5. 권장 설정

| 항목 | 권장 | 이유 |
|---|---|---|
| **엔진** | 처리량 우선이면 **pscan** | GIL 우회, 코어만큼 선형 |
| **워커 수**(`scan_workers`) | 기본 **4**(코어 수에 맞춰 조정) | 스레드는 과다해도 GIL로 정체 |
| **백엔드** | `native`(기본) | `du`는 외부 프로세스 의존 |
| **fold_depth** | 깊은 트리에서만 ↑ | 납작한 트리엔 무의미 |
| 워커 권장값 | `/api/recommend-workers` 참고 | 서버 메모리/코어 기준 산출 |

> 짧은 주기로 여러 NAS를 예약 스캔하면 동시에 시작돼 **GIL/단일 DB 경합**이 커진다.
> → **예약 시차 배치**(stagger)로 간격형 예약의 위상을 분산한다(`settings.stagger_schedules`).

### 5.1 오토튜닝 — 고정 6단 사다리(웹/서버 온디맨드)

새 스캔의 **🔬 오토튜닝**(대시보드)은 아래 **고정 6단계**를 각 기본 8초씩 **실측 비교**해 가장 빠른 조합으로
자동 시작한다(`autotune.DEFAULT_LADDER`):

| 단계 | 구성 | 노림수 |
|---|---|---|
| 단일 | (1, 1) | 기준선 |
| 8프로세스 | (8, 1) | GIL 우회(프로세스만) |
| 8프로세스 × 8스레드 | (8, 8) | 프로세스 + NFS 왕복 지연 은닉 |
| 16프로세스 | (16, 1) | 코어 많은 장비 확장 |
| 16프로세스 × 8스레드 | (16, 8) | 2단 병렬 확장 |
| 32프로세스 | (32, 1) | 고코어 상한 탐색 |

- 6단×8초 ≈ **48초** 측정. 32프로세스는 코어 적은 장비에선 오버서브스크립션이라 그 단계가 느리게 측정되지만,
  **튜너가 실측 처리량으로 최적을 자동 선택**하므로 결과는 안전하다(느린 단계는 안 뽑힘).
- 라이브러리 `autotune.default_candidates()`(프로그램/테스트용)는 파라미터화된 별도 규칙이다 — 웹/서버 온디맨드는
  위 6단 고정을 쓴다.

## 6. 6 PB 규모의 ‘진짜 답’ — 네이티브 메타데이터 (미검증)

- **6 PB를 파일 단위로 전수 stat 하는 것은 물리적으로 비현실적**이다(3장 한계가 그대로 곱해진다).
- 진짜 답은 **Isilon 네이티브**다 — 파일을 걷지 않고 클러스터 내부 메타데이터로 조회:
  - **SmartQuotas 어카운팅 쿼터**: 디렉터리 용량 즉시 조회.
  - **FSA / InsightIQ**: 파일시스템 분석 메타데이터.
- 이때 이 도구의 역할은 스캐너가 아니라 **네이티브 메타데이터를 모아 통합·시각화하는 컨트롤 플레인**이다.
- **정직 고지**: 네이티브 연계의 구체 수치는 **실 클러스터 없이는 미검증**이다. PoC에서 클러스터 메타데이터로 확정하는 것을 전제로 한다.

---

## 7. 측정 방법(재현용)

- 진단: `strace`(syscall 분포)·`gdb`(스레드 스택)로 직렬화 지점 확인.
- 비교: 같은 트리에서 **스레드 vs 프로세스** 워커 수를 바꿔 처리량(stat/s) 측정.
- 도구: 대시보드의 **‘처리량 추이’**·**오토튜닝**(`benchmark_workers`)로 현장에서 재측정 가능.

수치는 환경(코어 수·NAS 지연)에 따라 달라진다. **현장에서 한 번 측정**하고 그 값으로 결정하라 — 이 문서의 배율은 **방향**이지 보증이 아니다.
